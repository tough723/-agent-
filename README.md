# 智能 OnCall Agent（Java 版）

基于 **AI Agent + RAG 知识库 + 工具调用**，自动化处理运维告警全生命周期：
发现告警 → 排查 → 处置 → 闭环 → 沉淀知识。

> **这个系统能改生产环境。** 它的全部价值取决于"它不会做错事"这个信任，
> 而这个信任不能靠 prompt 保证，只能靠代码结构保证。
> 这句话是整个项目的地基，详见 [§3 项目基石](#3-项目基石)。

## 3. 项目基石

**单一强制点（single enforcement point）**：所有 AI 发起的写操作，
必须穿过 `GuardedToolCallback` 这一个不可绕过的关卡。

```
        LLM 决定调用工具
                │
                ▼
   ┌─────────────────────────┐
   │   GuardedToolCallback   │  ← 七道关卡，全在这里
   │  ① 默认拒绝（未注册即拒）│
   │  ② kill switch          │
   │  ③ 参数夹紧              │
   │  ④ 幂等                  │
   │  ⑤ 审批闸门              │
   │  ⑥ 超时 / 熔断           │
   │  ⑦ 审计                  │
   └─────────────────────────┘
                │
                ▼
            真实工具
```

**为什么这是基石而不是"安全模块之一"**：

- 其他所有控制（策略表、放权等级、审批流、审计）都**假设**这个关卡会被执行。
  关卡一旦被绕过，它们全部变成装饰。
- 因此有一道架构约束（F9）：**用 ArchUnit 禁止在网关之外直接调用
  `ToolCallback.call`**。没有这道约束，基石就是自愿遵守的君子协定。
- **最大的威胁是 MCP 工具**：它们在运行时才拉取，注解式风险分级看不见它们。
  所以 MCP 必须关掉自动注册（`toolcallback.enabled=false`，默认是 true），
  改为显式纳管并打 `mcp:<server>:` 前缀。

**第二块基石**：配置声明表（`OnCallConfigRegistry`）是唯一事实来源。
它让系统在不发版的情况下可调，同时让"什么能改、改的边界在哪"变成代码里可验证的东西。

## 4. 模块结构

```
oncall-agent (parent)
├── oncall-domain          纯 Java，零依赖    状态机 / 风险等级 / 放权闸门
├── oncall-config          纯 Java，零依赖    配置治理与前端可配置化
├── oncall-config-admin    Spring Web         配置治理的 REST 接入层
└── oncall-tool-gateway    Spring AI          工具调用安全核心 ← 基石所在
```

依赖方向严格单向。**`oncall-domain` 与 `oncall-config` 生产代码零外部依赖**是
硬约束：它们的逻辑必须能脱离 Spring 单元测试。HTTP 绑定、JDBC 实现都是适配器，
放在各自的 admin / store 子包或独立模块里。

## 6. 一条不能违反的规矩

**配置项能做成前端可交互的，就不要写死在后端**——兜底机制的配置除外。

落地为 `ConfigTier` 三级：`RUNTIME_HOT`（23 项，前端主战场）/
`REQUIRES_MIGRATION`（8 项，必须带迁移提示）/ `BACKEND_ONLY`（8 项，键名都不外泄）。

判据不是"这个参数重不重要"，而是**"改了它会发生什么"**。
